# Корпус статей поддержки

Здесь должны храниться только одобренные статьи, которые можно использовать для ответов клиентам. В репозитории корпуса пока нет: BANKING77 содержит тексты обращений и метки намерений, но не ответы службы поддержки.

## Формат

Создайте `articles.jsonl`: один JSON-объект на строку, UTF-8. Обязательны поля `id`, `title`, `content`, `source`, `updated_at`, `language`, `owner`, `license`, `status`.

`id` должен быть стабильным и уникальным. `source` должен позволять оператору открыть первоисточник. `updated_at` фиксирует дату обновления в формате `YYYY-MM-DD`. `language` использует код вроде `en` или `ru`. `owner` — команда или подразделение, отвечающее за статью. `license` фиксирует разрешение на использование или применимую лицензию. `status` должен быть `approved`; черновики загрузчик отклоняет. В `content` помещается текст статьи после проверки владельцем базы знаний.

```json
{"id":"card_payment_reversal","title":"Card payment reversal","content":"Approved support instructions...","source":"https://support.example.com/card-payment-reversal","updated_at":"2026-10-20","language":"en","owner":"Payments Support","license":"internal-approved","status":"approved"}
```

Пример демонстрационный: замените источник, владельца, лицензию и содержание на фактические одобренные данные. Не загружайте этот текст как реальную инструкцию.

Не добавляйте пароли, персональные данные клиентов, внутренние заметки, закрытые инструкции или материалы без подтверждённого права использования. Сохраняйте лицензию и владельца документа. Файлы `articles.jsonl`, `queries_calibration.jsonl`, `queries_holdout.jsonl` и созданный `reports/knowledge_audit.json` исключены из Git: корпус и поисковые запросы могут содержать внутреннюю информацию или персональные данные. В репозиторий следует отправлять код, схему и обезличенные сводки, если их разрешено публиковать.

## Первый retrieval baseline

`src/rag/retriever.py` проверяет JSONL, разбивает документы на фрагменты до 900 символов с перекрытием 120 символов и предоставляет два лексических ранжировщика: word TF-IDF unigram/bigram и BM25. В обоих случаях результат содержит `score` и `score_type`; TF-IDF выдаёт cosine similarity, BM25 — свой ранжирующий балл. Ни один score не является вероятностью ответа. Порог релевантности не задан: его нужно определить на отдельном наборе запросов и размеченных релевантных статей.

Для оценки поиска подготовьте два файла: `queries_calibration.jsonl` для выбора ранжировщика/порога и `queries_holdout.jsonl` для финальной оценки уже зафиксированного решения. Каждый содержит поле `query` и `relevant_document_ids`. Каждая строка — один вручную составленный запрос; список содержит все ID статей, которые эксперты считают релевантными. Если статьи с ответом нет, укажите пустой список. Пример формата (ID нужно заменить на реальные):

```json
{"query":"How can I reverse a card payment?","relevant_document_ids":["card_payment_reversal"]}
{"query":"Can I change my shoe size?","relevant_document_ids":[]}
```

Строки нужно вручную разделить по файлам, сохраняя одинаковый формат. Не кладите одинаковый вопрос или близкие переформулировки одного обращения в оба файла; все варианты одного семантического запроса должны остаться в одной части. По возможности сохраняйте в обеих частях разнообразие языков и типов намерения, включая запросы без ответа.

Положительные запросы участвуют в Recall@5 и MRR. Recall@5 для запроса — доля размеченных релевантных статей, найденных среди первых пяти уникальных документов; MRR — обратная позиция первого релевантного документа, усреднённая по положительным запросам. Запросы без ответа учитываются отдельно и не включаются в эти две метрики: для них нужно отдельно разрабатывать и оценивать порог отказа. Подбор ранжировщика и threshold выполняется только на calibration. После фиксации обоих решений holdout просматривается один раз и не используется для новых настроек. Реализация находится в `src/rag/evaluation.py`, а сравнение — в `notebooks/02_retrieval_exploration.ipynb`.

Для BM25 notebook перебирает небольшую исследовательскую сетку `k1` и `b` только на calibration. Это не исчерпывающий поиск параметров: при малом количестве размеченных запросов не стоит выбирать чрезмерно сложную конфигурацию. Зафиксируйте параметры вместе с методом и порогом до открытия holdout.

Сначала измерьте метрики на экспертных запросах, затем решите, нужны ли символьные признаки, BM25 или эмбеддинги. Сравнивайте варианты на одинаковой выборке и разметке. Не оценивайте retrieval только по примерам из корпуса.

Для отказа при слабом совпадении используйте `sweep_abstention_thresholds` из `src/rag/evaluation.py`. Положительные и отрицательные запросы должны быть представлены в отдельной калибровочной выборке. Функция перебирает пороги top-1 score для выбранного ранжировщика и показывает coverage, precision/recall/F1 корректно подтверждённых ответов, unsafe accept rate и долю принятых запросов без ответа. TF-IDF и BM25 требуют разных порогов из-за разных шкал. Это исследовательская калибровка: выбранный порог нужно зафиксировать и отдельно оценить на новых запросах. Не подбирайте порог и не заявляйте качество на одной и той же выборке.

## Проверка корпуса и актуальности

Запустите `python -m src.rag.audit --input data/knowledge/articles.jsonl --output reports/knowledge_audit.json`. Аудитор валидирует формат, обязательные метаданные, дату и статус, затем считает документы по языкам, владельцам и лицензиям. Он отмечает повторяющиеся заголовки/тексты и статьи старше срока проверки. По умолчанию срок равен 365 дням; это очередь на ручную проверку владельцем, а не автоматическое признание документа устаревшим. Срок можно изменить через `--review-after-days`. Для просмотра результата в PyCharm откройте `notebooks/04_knowledge_audit.ipynb`.
